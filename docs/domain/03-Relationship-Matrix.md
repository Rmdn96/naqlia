## 1. Purpose

This matrix defines logical cardinality, aggregate ownership, deletion/cascade behavior, reference semantics, and business constraints. Physical foreign keys, join structures, constraint syntax, and indexes are designed later, but MUST enforce these meanings.

## 2. Relationship Conventions

| Term               | Meaning                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| `1:1`              | Exactly one on each side once the relationship is established                                            |
| `1:0..1`           | Parent may have zero or one child/reference                                                              |
| `1:N`              | One parent to zero or more children unless a minimum is stated                                           |
| `M:N via entity`   | Logical many-to-many resolved by the named association entity                                            |
| Owned child        | Created/re-parented only through aggregate root; same Organization required                              |
| Live reference     | Current referenced record is consulted; historical use also captures version/key when meaning can change |
| Snapshot reference | Historical record stores the accepted values/version; later source changes do not alter it               |
| Restrict           | Parent retirement/destruction is blocked while required relationship exists                              |
| Retain             | Child/history survives parent closure/retirement under shared retention                                  |
| Draft cascade      | Unpublished/unissued, unreferenced draft children may be discarded with the draft root                   |

Global rules:

1. All tenant-owned relationships require the same immutable `organization_id`; RLS is not a substitute for referential tenant integrity.
2. Cross-Organization relationships are limited to Organization Connection, Resource Share, platform control records, and explicitly approved integration/audit targets.
3. Re-parenting an entity to another aggregate or Organization is prohibited. Correction creates a replacement/link and retains provenance.
4. Deleting a parent MUST NOT cascade over issued, accepted, converted, completed, financial, event, audit, communication-attempt, document-version, or security evidence.
5. Every logical M:N relationship uses an association entity with provenance, uniqueness, validity, and same-Organization checks.
6. Closed target allowlists are permitted only for Resource Share, Document Association, Verification Challenge target, External Reference, Workflow subject, Audit target, and Legal Hold Target. Each requires ownership validation and orphan reconciliation.

## 13. Cascade and Reference Decision Table

| Parent condition                            | Child/reference behavior                                                                                                                             |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unsubmitted/unreviewed draft abandoned      | Draft-only owned children MAY be deleted under bounded cleanup if no event, approval, audit, external delivery, or business reference exists.        |
| Mutable master retired                      | Active dependent creation is blocked; historical references remain; live selectors omit retired record.                                              |
| Configuration/catalog version superseded    | New operations resolve the new effective version; existing Lead/Quotation/Order facts retain captured key/version/content.                           |
| Customer closes or privacy request succeeds | Access is closed; eligible profile/contact/address data is deleted/anonymized; legally/operationally required snapshots and events remain minimized. |
| Lead/Quotation/Order/Execution terminal     | All children/history retained under policy; no cascade deletion.                                                                                     |
| Organization offboarding                    | Intake and access stop; records follow approved export/retention/legal-hold/destruction plan; no ordinary recursive cascade.                         |
| Legal Hold active                           | All applicable archive/destruction/erasure operations are blocked or adapted according to legal authority; the attempt is audited.                   |
| Derived report/export expires               | Artifact/projection MAY be deleted; source facts, definition version, access audit, and minimized execution evidence remain.                         |

## 14. Relationship Verification Gate

Physical design MUST produce tests for every relationship covering minimum/maximum cardinality, same-Organization enforcement, uniqueness, forbidden re-parenting, lifecycle validity, current/effective overlap, delete/retire behavior, historical snapshot stability, concurrent creation/update, closed-target allowlist, RLS denial, and retention/legal hold. No relationship may rely only on application convention.
