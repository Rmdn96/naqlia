## 1. Purpose

This catalog defines business fields, required/optional status, validation, query behavior, classification, and display fields for every logical entity. It deliberately assigns no SQL type, storage representation, column default, index, or physical nullability syntax. Physical design MUST preserve the business meaning and may split a logical structured value into reviewed physical structures.

## 2. Common Field Profiles

Every entity inherits one profile plus the domain-specific fields in its row.

Query notation in entity tables:

- `S:` searchable fields for authorized text/reference lookup;
- `F:` filterable fields for approved work queues/reports;
- `O:` sortable fields with deterministic tie-breaker by stable identity;
- `—` means no direct general-purpose query; access is by parent/correlation only.

Search never means public discovery. Sensitive fields require purpose-bound exact/normalized lookup, masking, minimum result set, and abuse monitoring. Unbounded free-text, arbitrary sort, and sensitive substring search are prohibited.

Classification notation: `PUB` approved public, `INT` internal, `CONF` confidential, `REST` restricted. “Display” lists the preferred human-facing values; identifiers remain available for authorized support only.

## 14. Field Validation Gate

Physical design MUST document, for every field above, its approved physical name, representation, nullability, default behavior, normalization, classification, encryption/masking, retention, constraint, RLS exposure, audit handling, API serialization, localization, and index/access-path decision. A technical representation may differ from this logical catalog only if it preserves every business rule and is recorded in the physical design or ADR.
